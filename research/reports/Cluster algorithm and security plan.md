# Read less, trust provider verdicts, measure everything

Date: 2026-10-20. Built from the six notes in `research/research_notes/Cluster algorithm and security plan/` (codebase audit at HEAD `e9db356`, provider and vendor detection techniques, attack trends, scan speed, sorting and cleanup UX, threat-intelligence APIs). It reuses still-valid findings from the sender algorithm deep dive and the unsubscribe grouping and filing reports. Code references are `path:line` relative to `/home/user/cluster`. External sources are linked inline. Labels: **[verified]** = read in code or on the cited primary page; **[secondary]** = from search extracts, vendor marketing or press; **[inference]** = our reasoning or arithmetic, not measured. Many provider pages were reachable only through search-engine extracts during research, and the notes say where.

**Bottom line.** Cluster's biggest speed problem is that it reads every message. Its biggest accuracy problem is that nothing is measured. Its biggest missed opportunity is that it ignores verdicts Microsoft already writes into headers Cluster fetches. On Gmail, the first full index build still issues one 20-unit `messages.get` per listed message and per Sent message. After the "fetch one, count many" census, every claimed id is read anyway (`src/lib/mailSync.ts:307-309`). That works out to roughly **510,000 units and at least 85 minutes** for a 20,000-message mailbox, against a 20-minute target. Making the detail phase lazy should cut that by about **4-5x** to roughly 20-25 minutes. It should also raise the number of new users per day that the project-wide **80M units/day** ceiling can serve from about 157 to about 800 **[inference]**. On Outlook, Cluster already `$select`s `internetMessageHeaders` (`src/lib/providers/outlookProvider.ts:141`) but never parses `X-Forefront-Antispam-Report` or `X-Microsoft-Antispam`. Those headers carry Microsoft's own SCL, BCL, phish, spoof, impersonation and first-contact verdicts ([Microsoft Learn](https://learn.microsoft.com/en-us/defender-office-365/message-headers-eop-mdo)). Security today is 11 hand-weighted header rules with six registered false positives and false negatives and no labelled evaluation set. Attack data shows that the mail which gets past Gmail and Outlook is mostly *authenticated*: compromised accounts, abused SaaS invoices, link-less callback scams and SVG attachments. Cluster's next accuracy gains therefore come from relational signals (brand versus domain, phone numbers, first contact, fake threads), not from re-checking SPF and DKIM. **On VirusTotal: do not build it in.** The free Public API allows 4 lookups a minute and 500 a day, may not be used in commercial products, would expose a shared key, and shares anything submitted with the security community. The only acceptable form is an opt-in, bring-your-own-key, per-click **lookup** of a domain, with no submissions. Cluster should get its threat intelligence from abuse.ch and phishing feeds pulled centrally into its existing signed GitHub Pages dataset, so no per-message data ever leaves the device.

## Cluster today: a solid index, a full read, and uncalibrated rules

### The scan pipeline already has the hard plumbing

Most of the infrastructure that fast scanners need is already in place. Gmail runs on a persistent IndexedDB mail index capped at 20,000 rows per account (`src/lib/mailIndex.ts:14`). After the first build it is kept current by `history.list` at 2 units a page, with a 404 fallback to re-listing (`src/lib/mailSync.ts:120-130`). Label-only changes such as read, star and category are applied from history without re-reading (`src/lib/mailSync.ts:340-356`). Every call reserves its cost in a cross-context quota ledger. The ledger uses a 60-second window and a budget of **5,500 units**, 500 below Google's ceiling, and it penalises a full window after a rate-limit 403 survives its retries (`src/lib/gmailQuotaLedger.ts:17-24`, `:120-125`). Retries honour Retry-After (`src/lib/httpRetry.ts:50-76`), and `batchModify` works in 1,000-id chunks. The first screen appears after 150 unpaced reads, about 3,000 units (`src/lib/mailSync.ts:257-272`). The census runs one `from:(addr) newer_than:Nd` search per sender worth counting and marks the returned ids "claimed" (`src/lib/mailSync.ts:436-548`). Because the OAuth scope is `gmail.modify` (`manifest.json:41-44`), the `q=` search that the census depends on is available. The notes' warning that `q=` is unusable under `gmail.metadata` ([Nylas](https://cli.nylas.com/guides/gmail-api-search-query)) does not apply to Cluster.

The waste is in step 9. The census only changes the order of the reads; it does not skip any. The detail phase then reads every claimed-but-unread id: `rest = [...discovery.pending, ...upgrade]; readInto(..., "detail")` (`src/lib/mailSync.ts:307-309`). With Sent backfill capped at 5,000 (`src/lib/mailSync.ts:185`), a full first build costs about 20 × (N_listed + N_sent) units. For a 20,000-message mailbox that is about **400,000 + 100,000 + ~10,000 in list and search calls ≈ 510,000 units**. At Google's hard limit of **6,000 units per user per minute** ([Gmail usage limits](https://developers.google.com/workspace/gmail/api/reference/quota)) that takes at least 85 minutes. In practice it is closer to two hours, because the dashboard waits for 1,500 units of headroom (`src/dashboard/dashboard.ts:604-611`) **[inference from verified code]**. The suggestions engine already refuses to act on census-only mail (`src/lib/suggestions.ts:18-20`). That is the correct safety property, and it means the detail reads are mostly prefetch for actions the user may never take.

Outlook lags further behind. The provider object lacks `listChangesSince`, `getChangeCursor`, `listMessageIdsFrom` and `listSentMessageIds` (`src/lib/providers/outlookProvider.ts:681-705`). As a result, every dashboard open re-lists the inbox and re-reads every message younger than 7 days (`src/lib/mailSync.ts:300`). It has no census, and background triage falls back to the legacy 150-message scanner (`src/background.ts:357-376`). The Graph delta path with 410 handling exists, but it feeds only the legacy incremental summaries (`src/lib/incrementalSync.ts:20-60`), not the index. Outlook also lists only `mailFolders/inbox` (`src/lib/providers/outlookProvider.ts:85-97`). On Gmail, Social and Forums are outside the index scope, which a registered `it.fails` test flags as a known gap (`src/lib/providers/gmailProvider.normalize.test.ts:117`).

### Sorting and cleanup are deterministic, English-only and inconsistently gated

Message kind is decided by first-match English subject regexes (`src/lib/messageKind.ts:7-26`). The test suite registers four known misfires: "Free delivery" counts as shipping, a "tracking" newsletter counts as shipping, a "statement" newsletter counts as a receipt, and "Please verify your device" is not treated as an OTP (`src/lib/algorithmAudit.test.ts:133-142`). Category comes from a hand list of about 120 domains (`src/lib/domainCategories.ts:27-66`). Sender kind is a 70% majority vote (`src/lib/senderProfile.ts:18`). Engagement is the UNREAD-flag share after a 3-day grace period (`src/lib/senderProfile.ts:251-282`). That signal is biased: mail Cluster itself filed out of the inbox stays unread and reinforces "ignored" (open item U13). No confidence scores exist anywhere in the sort path.

The protection gate is strong where it is used: starred, IMPORTANT, known correspondent, active offer, receipt or shipping, sensitive subject, and "other" with no bulk signal (`src/lib/protectionPolicy.ts:46-86`). It is not used everywhere. `buildSortPlan` excludes only starred mail (`src/lib/autoSort.ts:67`). Smart-view archive checks only `isProtected` (`src/lib/smartViews.ts:53-58`). Rules exclude starred mail and, for trash, IMPORTANT and non-code OTPs, but receipts can still be trashed, a registered bug (`src/lib/rules.ts:147-171`, `src/lib/algorithmAudit.test.ts:321`). Time limits skip only known senders and starred mail (`src/lib/inboxTimeLimits.ts:79-105`). The automation that would cut steps (Screener, inbox time limits, auto-quarantine) is off by default (`src/lib/settingsStore.ts:188,204,215`). Reaching a sorted inbox takes roughly 5-8 clicks, through preview, label-collision prompts, confirm and a separate "Keep sorting" opt-in (`src/dashboard/sortInbox.ts:655-686`; the count is inferred, not walked through).

### Security is eleven ordinal weights that nobody has scored

The threat model sums 11 signal kinds with hand-set weights, plus 1 for each high-confidence signal (`src/lib/threatSignals.ts:444-471`). A hold needs a score of 6 or more and either a decisive kind or two distinct kinds (`src/lib/verdict.ts:62-66`, `:186-192`). The kinds are blocklisted domain (6), freemail brand claim (5), lookalike (4), link mismatch (4, Deep scan only), failed authentication (3), brand impersonation (3), reply-to mismatch (3), risky attachment (3), identity change (3), punycode (2) and lure language (2). The building blocks the coordinator listed are real and verified. They include an RFC 8601 tokenised Authentication-Results parser that trusts only `mx.google.com` on Gmail (`src/lib/emailAuth.ts:31-170`), confusables plus punycode plus edit-distance lookalikes, combosquat detection, and Ed25519-signed remote datasets (`src/lib/datasetSignature.ts:26-29`).

The weak spots are just as concrete. The test suite registers three false positives: a person named Chase on gmail.com is held, chess.com is flagged as a chase.com lookalike, and "Start-Ups Weekly" matches UPS. It also registers three false negatives: "Microsoft Account Team" @outlook.com, "Google Security" @gmail.com and "Apple Support" @icloud.com score zero, because those free-mail domains appear in the brands' own domain lists (`src/lib/algorithmAudit.test.ts:194-211`, `src/lib/data/brandDomains.json`). An offline re-implementation of the edit-distance rule also flagged discovery.com, adobe.io, amazon.fr, google.ca, fedex.ca, tmobile.com and usps.gov at high confidence. These are legitimate domains or the brand's own country domains. Display names are not NFKC-normalised or stripped of zero-width and bidi characters, so "PayPaI" evades the brand check. Two free-mail lists disagree, one with 7 domains and one with 16 (`src/lib/threatSignals.ts:130` versus `src/lib/freeMail.ts:1-21`). The blocklist holds only 388 URLhaus malware hosts, and its hand seed is empty (`src/lib/blocklistSeed.ts:11-14`). The 7-point decisive signal is therefore mostly dormant, because malware-distribution hosts rarely appear in From addresses **[inference]**. Outlook authentication trust still accepts any authserv-id ending in `outlook.com` (`src/lib/emailAuth.ts:36-41`). Outlook also reads `sender`, not `from` (`src/lib/providers/outlookProvider.ts:141`). Background security scoring covers only the newest 100 inbox messages per 30 days, every 6 hours (`src/background.ts:62-63`). Mail Cluster filed out of the inbox is never re-scored (`src/lib/providers/gmailProvider.ts:51`).

Most important, **there is no labelled precision/recall set**. The repo has a synthetic fixture builder (`src/test/mailFixtures.ts`), safety invariants, more than 20 `it.fails` known bugs and a single shape contract (`src/lib/pipeline.contract.test.ts:67-68`). The evaluation harness proposed on 10-05 (about 300 labelled items, with floors of protection recall ≥ 0.99, high-risk threat precision ≥ 0.9 and OTP precision ≥ 0.95) was never built (`research/2026-10-05-algorithm-audit-and-upgrades.md:787-826`). `scripts/bench-pipeline.mts` measures only CPU stages and says so (`scripts/bench-pipeline.mts:1-8`). Every threshold in this section is therefore untested. That includes the 0.7 majority, the 0.1 and 0.4 open-rate cutoffs, edit distance 2 and HOLD 6.

## What the leaders actually do, and what slips past them

### Microsoft hands Cluster its verdicts; Gmail hands it authentication results

Gmail's filtering runs before delivery and publishes no score. Its ML text models, such as RETVec, raised spam detection by 38% and cut false positives by 19.4% ([Google Security Blog](https://security.googleblog.com/2023/11/improving-text-classification.html)). Alongside them run Safe Browsing, attachment sandboxing and sender reputation. A client sees only the results: the `Authentication-Results: mx.google.com` line, the ARC chain on forwarded mail, the SPAM label, and the compliance artefacts the 2024 bulk-sender rules made mandatory. Those rules require SPF and DKIM, aligned DMARC, and RFC 8058 one-click unsubscribe for marketing mail from senders of more than 5,000 messages a day, with transactional mail exempt ([Google sender guidelines FAQ](https://support.google.com/a/answer/14229414)). `List-Unsubscribe-Post: List-Unsubscribe=One-Click` under a DKIM signature is therefore a high-precision marketing signal, and its *absence* is a transactional hint. One Gmail quirk matters for security: Gmail fails open on SPF `temperror`. Spoofs of domains with no SPF record can reach the inbox carrying `Received-SPF: temperror`, and Sublime ships a rule for exactly this ([sublime-rules](https://github.com/sublime-security/sublime-rules/blob/main/detection-rules/headers_spf_temp_error.yml)). Cluster requests neither `Received-SPF` nor `ARC-Authentication-Results` today (`src/lib/gmailApi.ts:381-394`, `src/lib/headerFields.ts:78-88`). Adding them is free, because Gmail charges per call, not per header ([Gmail usage limits](https://developers.google.com/workspace/gmail/api/reference/quota)).

Microsoft is far more generous. Exchange Online Protection stamps every inbound message with `X-Forefront-Antispam-Report` and `X-Microsoft-Antispam` ([Microsoft Learn](https://learn.microsoft.com/en-us/defender-office-365/message-headers-eop-mdo)). The first carries SCL (−1 to 9, where 5-6 is spam and 9 is high-confidence spam), SFV (SPM/NSPM), CAT (PHSH, HPHSH, SPOOF, UIMP, DIMP, GIMP, BIMP, BULK and others), SRV:BULK, and SFTY:9.25 for first contact. The second carries BCL (0-9) and PCL. `Authentication-Results` adds `compauth=pass|fail|softpass reason=NNN`. Here 000 is an explicit DMARC failure and 001 is an implicit failure decided by spoof intelligence ([Microsoft Learn: anti-spam troubleshooting](https://learn.microsoft.com/en-us/defender-office-365/anti-spam-policies-troubleshooting)). Microsoft's own pages contradict each other on reason codes 002 and 010, so Cluster should key only on 000, 001 and the 1xx pass range ([Microsoft Learn: ARC](https://learn.microsoft.com/en-us/defender-office-365/email-authentication-arc-configure)). Reading these values through Graph's `internetMessageHeaders` is a documented pattern ([Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/1397679/currently-using-microsoft-graph-wanted-to-know-whe)). Three caveats need a live test before any of this ships. First, nobody confirmed that Graph returns the full header set unfiltered. Second, an attacker can plant a fake `X-Forefront-Antispam-Report` lower in the header block, so only the copy stamped by the recipient's own tenant counts. Third, the same headers appear on Gmail mail that passed *through* a sender's Microsoft 365 tenant, where they describe the sender side and must be ignored.

### Vendors win with history gates and explicit negations, not cleverer rules

Commercial vendors lead in three areas: cross-customer intelligence (Abnormal VendorBase, IRONSCALES crowd reports, Cloudflare's crawling of attacker infrastructure that is still being set up), per-relationship baselines, and click-time or sandbox detonation. None of these can run in a serverless extension ([Abnormal VendorBase](https://abnormal.ai/resources/vendorbase-security-email-supply-chain); [Cloudflare](https://blog.cloudflare.com/replace-your-email-gateway-with-area-1/); [Proofpoint TAP](https://www.proofpoint.com/sites/default/files/data-sheets/pfpt-us-ds-targeted-attack-protection.pdf)). What Cluster *can* copy is Sublime Security's open rule set, read first-hand at 1,335 rules ([sublime-rules](https://github.com/sublime-security/sublime-rules/tree/main/detection-rules)). The pattern is consistent. Cheap structural predicates are combined with a **sender-history gate** (301 rules call `profile.by_sender*`, testing for a new sender or one the user never wrote to) and with **explicit negations** for known false-positive sources. Those sources are Gmail auto-forwards (`+caf_=`), list mail carrying List-Unsubscribe and "via", real replies with References, bounces, and high-trust domains that pass DMARC. Sublime's lookalike rule uses edit distance **1** with a second-level domain longer than 3 characters and an unsolicited sender ([lookalike_sender_domain.yml](https://github.com/sublime-security/sublime-rules/blob/main/detection-rules/lookalike_sender_domain.yml)). Its Apple rule fires on a display name near "apple developer" only when the domain is not apple.com *and* the sender is not among the user's own recipients ([sublime-rules](https://github.com/sublime-security/sublime-rules/tree/main/detection-rules)). Cluster's distance-2, ungated rule is what flags chess.com.

The only peer-reviewed production result shows why the gate matters. BEC-Guard's header impersonation classifier alone had **11.7% precision**. Gated by a second independent signal it reached **98.2%**, and **59.9% of attacks carried no link** ([Cidon et al., USENIX Security 2019](https://www.usenix.org/system/files/sec19-cidon.pdf)). Warnings have a cost too: users obeyed **59-67% of false warnings** ([Petelka 2025](https://jpetelka.github.io/files/ieee_2025_phishing.pdf)). Each false hold therefore trains the wrong habit, which is why the plan below is built around precision.

### The residual threat is authenticated, link-less and brand-themed

Google says Gmail blocks more than 99.9% of spam, phishing and malware **[vendor]** ([BleepingComputer](https://www.bleepingcomputer.com/news/security/google-says-gmail-now-blocks-99-9-percent-of-spam-and-phishing-emails/)). What gets through skews toward mail that passes authentication. In KnowBe4's telemetry **57.9% of phishing came from compromised accounts** ([KnowBe4](https://blog.knowbe4.com/key-takeaways-from-the-2025-phishing-threat-trends-report)). In Cisco Talos Q2 2025, **75% of phishing engagements involved compromised identities** ([Talos](https://blog.talosintelligence.com/ir-trends-q2-2025/)). PayPal invoices created on PayPal arrive from genuine service@paypal.com, with the scam phone number in the merchant note ([Guard.io](https://guard.io/blog/paypal-scam-emails-7-fakes-making-rounds)). PayPal-branded lures were also sent through the DocuSign API ([Malwarebytes](https://www.malwarebytes.com/de/blog/news/2025/03/paypal-scam-abuses-docusign-api-to-spread-phishy-emails)). Callback (TOAD) invoices impersonating Norton, PayPal and Geek Squad push victims to call a phone number ([The Hacker News, citing Talos](https://thehackernews.com/2025/07/hackers-using-pdfs-to-impersonate.html?hl=en)). One IRONSCALES case came from a compromised school account, passed full authentication and a clean scan, and carried nothing but a phone number ([IRONSCALES](https://ironscales.com/threat-intelligence/compromised-school-account-toad-callback-pdf-clean-scan-auth-pass)). SVG attachments rose from about **0.1% of lures in 2024 to 4.9% in H1 2025** ([Hoxhunt](https://hoxhunt.com/blog/svg-phishing-email-attachments-mini-report)), yet `.svg` is missing from Cluster's risky list (`src/lib/riskyAttachments.ts:17-37`). New gTLDs hold 11% of the domain market but account for **51% of phishing domains**, led by .top, .xyz and .shop ([Interisle](https://interisle.net/)). Microsoft remains the most impersonated brand at about 23% in Q2 2026. LinkedIn, Google, Apple and Amazon follow, and ChatGPT billing lures entered the top 10 ([Check Point](https://blog.checkpoint.com/research/which-brands-are-impersonated-most-inside-the-q2-2026-brand-phishing-report)). For consumers, scams cause more losses than credential theft: imposter scams cost **$3.5B** in FTC 2025 data ([FTC](https://www.ftc.gov/news-events/news/press-releases/2026/03/ftc-testifies-joint-economic-committee-agencys-efforts-combat-fraud)) and BEC about **$3.05B** in IC3 2025 ([SpyCloud](https://spycloud.com/blog/fbi-internet-crime-report-2025/)). AI-written lures reached a 54% click-through rate against 12% for non-AI lures ([The Register](https://www.theregister.com/2025/10/16/ai_makes_phishing_45x_more_effective)), so typo heuristics are dead. Taken together, the evidence says that "passes DMARC" should be neutral, not reassuring. The detectors worth building are brand-versus-domain mismatch, phone numbers in subject or display name, a platform sender carrying a third-party brand, SVG and HTML attachments, new-gTLD senders, and first contact combined with financial urgency.

### Low-friction cleanup is a ladder, keyed on the sender

Every provider exposes correction per sender: Outlook's "Always move to Focused" and Sweep, Apple's "Categorize Sender", HEY's one-time Screener ([HEY](https://www.hey.com/how-it-works/); [WiseStamp on Sweep](https://www.wisestamp.com/blog/outlook-sweep/)). Gmail's July 2025 Manage subscriptions view sets the minimum bar: senders sorted by frequency, one click to unsubscribe, no confirmation ([Google Workspace Updates](https://workspaceupdates.googleblog.com/2025/07/manage-email-subscriptions-in-gmail.html)). The tools that cut the most steps climb a ladder. They auto-sort only reversibly, suggest with one-click accept, turn an accepted suggestion into a standing rule with a "processed N messages" count, and keep delete behind a confirm. Clean Email turns accepted suggestions into Auto Clean rules ([Clean Email](https://clean.email/help/basics/whats-new-in-clean-email-next)). SaneBox moves mail to a real folder, fails open, and learns from the Sent folder and from moves ([SaneBox](https://sanebox.com/help/155-how-does-sanebox-work)). Inbox Zero auto-archives the future mail of senders who ignore an unsubscribe ([Inbox Zero docs](https://docs.getinboxzero.com/essentials/bulk-email-unsubscriber.md)). UX guidance agrees: prefer undo to confirmation for reversible actions, and keep dialogs for irreversible ones, because overused confirmations train users to click through ([Primer](https://primer.style/product/components/confirmation-dialog/guidelines)). No vendor publishes thresholds or accuracy figures, so Cluster's thresholds have to come from its own evaluation set.

## The quota arithmetic: list and search are ~2,000 times cheaper per message than get

Under the May 2026 tier, `messages.list` costs 5 units for up to 500 ids, `history.list` 2 units, `labels.get` 1 unit and `messages.get` 20 units, against **6,000 units per user per minute**. There is also **1,200,000 units per minute per project** and an **80,000,000 units per day** project threshold ([Gmail usage limits](https://developers.google.com/workspace/gmail/api/reference/quota); [Nylas](https://cli.nylas.com/guides/gmail-api-quotas-2026) **[secondary for the project figures]**). A listed id costs 0.01 units and a fetched one costs 20, a ratio of 2,000:1. HTTP batching saves round trips but not units, and Google recommends 50 or fewer calls per batch ([Gmail batch guide](https://developers.google.com/workspace/gmail/api/guides/batch)). `threads.get` at 40 units only breaks even on threads of three or more messages, which bulk mail rarely forms **[inference]**.

| Scenario (Gmail, 20k inbox+promos+updates, 5k Sent, ~1,500 distinct senders) | Gets | Units | Wall time at 4,000-5,500 units/min |
|---|---|---|---|
| Today: quick 150 + Sent 5k + discovery + full detail | ~25,000 | ~510,000 | 93-128 min (≥85 at the 6,000 ceiling) |
| Lazy detail: quick 150 + discovery (≈1 per sender + batch waste) + Sent capped to 365 days (~2k) | ~4,000-5,500 | ~85,000-115,000 | 16-29 min |
| Lazy detail + q=-based protection sets + 1-3 samples per sender, Sent sampled | ~3,000-4,000 | ~65,000-85,000 | 12-21 min |
| Repeat sync, cursor valid | new mail only | a few hundred | seconds |

The rows are **[inference]** from the cost table and `src/lib/mailSync.ts`. Sender count and Sent size are assumptions to replace with real census numbers. The project ceiling makes this more than a user-experience issue. At 510,000 units per first build, 80M units a day covers only about **157 new users a day**. At about 100,000 it covers about 800 **[inference]**. On Outlook the constraint is requests, not units: **10,000 requests per 10 minutes and 4 concurrent requests per mailbox** ([Graph throttling limits](https://learn.microsoft.com/en-us/graph/throttling-limits)), with JSON `$batch` capped at 20 sub-requests that are throttled individually ([JSON batching](https://learn.microsoft.com/en-us/graph/json-batching)). Delta returns `$select`ed properties inline ([delta query](https://learn.microsoft.com/en-us/graph/delta-query-messages)), so listing is nearly free. The per-message GET is needed only for `internetMessageHeaders`. That GET should be sampled per sender, not run for every message younger than 7 days on every open. MV3 limits shape the implementation: the service worker dies after 30 seconds idle or after a single 30-second fetch ([Chrome docs](https://developer.chrome.com/docs/extensions/mv3/service_workers/service-worker-lifecycle)). Long builds must checkpoint the phase, pageTokens and historyId after each page. Cluster's index already does most of this.

## Threat intelligence that fits a no-server, free extension

The licensing constraints decide the architecture more than the technology does. The workable pattern is **central aggregation, local matching**. A GitHub Action runs under one maintainer key, pulls feeds, reduces them to registrable domains and hashes, signs the result with the existing Ed25519 mechanism, and publishes it to GitHub Pages. The extension already fetches from that one origin (`src/lib/remoteDataset.ts:12-17`), so users never contact a threat-intel provider and no message data leaves the device. This also answers the Chrome Web Store's 2026 "strictly necessary" rule for user data in the cleanest way, because no user data is transferred at all ([CWS policy updates 2026](https://developer.chrome.com/blog/cws-policy-updates-2026); [Limited Use](https://developer.chrome.com/docs/webstore/program-policies/limited-use)).

### The VirusTotal answer

Cluster should not ship VirusTotal as a built-in feature. Four reasons rule it out. **The quota is per key and tiny**: the Public API allows "500 requests per day and a rate of 4 requests per minute" ([VirusTotal](https://docs.virustotal.com/reference/public-vs-premium-api)). One embedded key would be exhausted by a few users and extracted from the bundle by anyone. **The terms exclude it**: the Public API "must not be used in commercial products or services" or in business workflows that do not contribute new files ([Wazuh quoting VT terms](https://documentation.wazuh.com/current/user-manual/capabilities/malware-detection/virus-total-integration.html) **[secondary]**). Premium pricing is quote-only. **Submissions are shared**: uploaded samples go to the corpus and to partners and premium subscribers ([VT privacy policy](https://docs.virustotal.com/docs/historic-privacy-policy)), which is incompatible with Cluster's stance for any URL or file taken from a user's mail. **It does not fit Cluster's data**: Cluster fetches attachment *names*, never bytes (`src/lib/providers/outlookProvider.ts:141-148`). A file-hash lookup would therefore first require downloading the attachment, which breaks the metadata-only promise. The remaining use is domain reports. Those overlap with what a signed abuse.ch and phishing-feed dataset gives every user for free and with no disclosure **[inference]**. If users ask for it, the acceptable form is narrow: an opt-in "Check with VirusTotal" button, a user-pasted key held in `chrome.storage.local`, `GET /api/v3/domains/{domain}` only (never `POST /urls` or `POST /files`), an optional host permission requested from a user gesture, and copy that says plainly that the domain goes to Google/VirusTotal. That is a power-user nicety at Phase 4, not a detection layer.

## Conclusion

The plan rests on one idea: stop paying for evidence someone else already computed. Gmail's search index can return id sets and counts for list-level prices, and Microsoft's filters have already decided spam, bulk, phish and first contact. Cluster's own reads and rules should be spent only where neither provider has an answer. That is the relational, authenticated-but-wrong residual: a contact's name on a new address, PayPal's real servers carrying a scammer's phone number, an SVG "voicemail". Commercial vendors spend their engineering there too. The ordering matters as much as the items. Lazy reads and harvested Microsoft verdicts are the cheapest large gains. The brand-model fix removes every registered false positive. Without the Phase 0 eval set and quota simulator, none of these gains can be shown, and every threshold stays a guess.

Two results were not obvious going in. First, quota is a growth constraint as well as a speed constraint. At today's per-user build cost, the project-wide daily ceiling caps onboarding at roughly 157 full builds a day, so lazy detail decides how fast Cluster can grow, not only how fast it feels. Second, the privacy stance and the licences point the same way. The feeds that allow free use (abuse.ch not-for-profit, Safe Browsing non-commercial, Tranco CC BY-NC) all fit best when pulled once in CI and shipped as a signed dataset. That is the mechanism Cluster already has, and it means users disclose nothing. VirusTotal fails both tests, so it stays out of the core.
