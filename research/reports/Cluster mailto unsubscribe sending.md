# Send mailto unsubscribes, but show them first

Date: 2026-10-16. Built from the four notes in `research/research_notes/Cluster mailto unsubscribe sending/`. It also uses the earlier report `research/reports/Cluster unsubscribe grouping and filing.md`, its notes, and the design note `research/2026-10-16-unsubscribe-and-grouping.md`. Where they disagree, the new notes win.

**Bottom line.** Cluster can send mailto unsubscribes itself on Gmail today with no new scope. The owner's draft plan is mostly right, but one part has to change. "Ask once, then automatic" breaks a Chrome Web Store rule and goes against RFC 6068 and RFC 2369. The store forbids sending messages for the user "without giving the user the ability to confirm the content." Both RFCs say the user should see the message before it goes. So Cluster needs a confirmation step on every run that lists each address, subject and body, with a "Send N emails" button. It must never send in the background or on a schedule. Five other gaps matter almost as much. Cluster must send from the address that is actually subscribed, or list servers like Mailman will ignore the request. It must use the body from the mailto URL when one is given, rather than always sending an empty body. It must sanitise the URL down to one To address, a subject and a body. It must watch replies, so it can catch bounces and "confirm your unsubscribe" emails. And it must word results honestly, because mailto is the slow method and US law allows 10 business days. Outlook needs `Mail.Send` to send at all, and some work tenants will block it. A draft that the user sends from Outlook on the web works with the current scopes.

## The standards make mailto a shown, sanitised, single message

Three RFCs set the rules. RFC 2369 defines List-Unsubscribe as a comma-separated list of URLs in angle brackets, **ordered by preference from left to right**. If an item is not a bracketed URL, that item and every later one should be ignored. A message may carry only one List-Unsubscribe field. The RFC also says "the user must have a chance to confirm any action before it is executed." If a dialog stands in for the raw message, it "MUST include an option for the user to review (and possibly modify) the message before it is sent" ([RFC 2369](https://www.rfc-editor.org/rfc/rfc2369.html), [RFC 2369 text, App. B](https://www.rfc-editor.org/rfc/rfc2369.txt)). Appendix B.1 adds that "the address that is subscribed should be used," and that the client should ask the user when it cannot tell which address that is.

RFC 6068 governs the mailto URL itself. Originator, routing, trace and MIME fields in the URL "MUST be ignored." Unknown fields "SHOULD be treated as especially suspect." Only Subject, Keywords and Body are "safe and useful in the general case." Values are percent-decoded once as UTF-8, and `+` is not a space. Line breaks are allowed only in the body. Most important for Cluster, a client "**SHOULD NOT send a message based on a 'mailto' URI without first disclosing**" it to the user ([RFC 6068](https://www.rfc-editor.org/rfc/rfc6068.html)). SHOULD NOT is not MUST NOT, so a client can depart from it. But the Chrome Web Store rule below removes that room.

RFC 8058 defines one-click as an HTTPS POST of `List-Unsubscribe=One-Click` and nothing else. **There is no one-click mailto.** A valid DKIM signature must cover the headers, and the POST must not run "without user consent" ([RFC 8058](https://datatracker.ietf.org/doc/html/rfc8058)). Google says it will "continue to support mailto links but they don't meet our one-click unsubscribe requirement," and it recommends that senders honour requests "within 48 hours" ([Google sender FAQ](https://support.google.com/a/answer/14229414)). That corrects the earlier report, which said the current Google pages did not state a timeframe. So the order for Cluster stays as it is now. A verified one-click POST comes first. Mailto comes second. A web link opened in a tab comes last. That departs from the strict leftmost rule, but it matches what major clients do and what RFC 8058 treats as the stronger path.

Cluster's current parser in `src/lib/unsubscribe.ts` falls short of these rules in four ways. It splits on every comma, so a mailto with two recipients or a comma in its subject breaks apart. It skips malformed items instead of stopping at them. It keeps the last mailto, not the first. And it stores the raw URL with no handling of its fields. None of this matters while Cluster only opens a compose window, because the user sees the result. It matters as soon as Cluster sends.

## Senders process mailto slowly, and many match on the From address

The receiving side splits into two groups. API email services mostly do not process mailto at all. SendGrid tells customers "it is your responsibility to receive and process these generated emails" ([Twilio SendGrid](https://www.twilio.com/docs/sendgrid/ui/sending-email/list-unsubscribe)). Postmark says the request goes to "the email address you've listed" and that mailto alone does not meet the 2024 Gmail and Yahoo rules ([Postmark](https://postmarkapp.com/support/article/1299-how-to-include-a-list-unsubscribe-header)). Amazon SES assumes the customer's own code handles the inbound mail ([AWS SES docs](https://docs.aws.amazon.com/ses/latest/DeveloperGuide/sending-email-subscription-management.html)). Salesforce Marketing Cloud unsubscribes the replying address when it finds unsubscribe words in the subject or the first 200 characters of the body ([Trailhead](https://trailhead.salesforce.com/content/learn/modules/send-management-in-marketing-cloud/set-up-reply-mail-management)).

Classic list servers are the other group, and they are the ones most likely to offer mailto only. GNU Mailman takes a message to `LISTNAME-leave@DOMAIN` "**from the address you want removed**," ignores the subject and body, then sends a confirmation email "to stop people from unsubscribing you without your permission" ([Mailman manual](https://list.org/mailman-member/node14.html)). Google Groups uses `+unsubscribe` and ignores subject and body. University help pages disagree on whether it then asks for confirmation ([UAlaska](https://service.alaska.edu/TDClient/36/Portal/KB/ArticleDet?ID=201), [CU Boulder](https://oit.colorado.edu/services/messaging-collaboration/google-workspace/help/groups/help/use-as-email-list)). List help pages report that requests from a different address than the subscribed one are discarded ([UUA](https://www.uua.org/node/28230), [LibreOffice list](https://www.libreoffice.org/lists/users/2011/msg05235.html)). Sympa reads the body as commands. In 2010 it rejected a Gmail-built request because the body still held `unsubscribe%20msitm` and an added footer ([Sympa archive](https://lists.sympa.community/arc/en/2010-08/msg00038.html)).

Four rules for the message follow from this. First, send from the address the mail was delivered to, which may be an alias. Second, use the URL's subject and body exactly when they are given, decoded once, because some lists depend on them (RFC 2369 shows `?body=unsubscribe%20list` as an example). When the URL has no subject, use "unsubscribe," since keyword parsers look for it and list servers ignore it. When it has no body, leave the body empty. Third, add nothing: no signature, no footer, no copy of the original subject, and no header naming Cluster. Fourth, do not set `Auto-Submitted`. RFC 3834 says it "SHOULD NOT be supplied for messages that were manually submitted by a human," and responders avoid replying to it, which could block the list's confirmation email ([RFC 3834](https://www.rfc-editor.org/rfc/rfc3834.html)). Send it as a new message, not a reply in the thread. Gmail only threads a send when `threadId`, `References`, `In-Reply-To` and a matching subject all line up ([Gmail threads guide](https://developers.google.com/gmail/api/guides/threads)), and none of that helps an unsubscribe.

There is precedent for a client sending from the user's own account. Apple Mail confirms first, then sends "from you" with an empty subject and a body naming the original message, and keeps a copy in Sent ([Spam Resource](https://www.spamresource.com/2023/02/faq-list-unsubscribe-on-apple-mail-on.html)). Gmail sends "an email from your account" after confirmation ([Android Central](https://www.androidcentral.com/apps-software/gmail-blue-unsubscribe-button-on-the-web)). Every documented example asks first. None sends unasked.

No independent study measures how many senders offer mailto only in 2023 to 2026. One vendor found 94.9% of 19,797 brands send a List-Unsubscribe header ([InboxEagle](https://www.inboxeagle.com/blog/list-unsubscribe-headers-spam-rates/)). Another says only 14% fully pass one-click, with no method given ([Unspam](https://unspam.email/articles/list-unsubscribe-header/)). Cluster should count this on the device.

## Gmail needs no new scope, Outlook needs Mail.Send, and the store needs a confirm

On Gmail, `users.messages.send` accepts `gmail.modify`, which Cluster already holds ([messages.send](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/send)). `settings.sendAs.list` accepts `gmail.settings.basic` or `gmail.modify`, so Cluster can read the user's aliases too ([sendAs.list](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.settings.sendAs/list?hl=en)). A send costs 100 quota units. Since 1 May 2026 the per-user limit is 6,000 units a minute, about 60 sends ([Gmail quota](https://developers.google.com/workspace/gmail/api/reference/quota?hl=en)). Quota is not the binding limit. Account sending limits are. Consumer Gmail allows **500 emails a day** ([Gmail Help](https://support.google.com/mail/answer/22839?hl=en)). Workspace allows **2,000 unique external recipients a day, or 500 on trial accounts**, over a rolling 24 hours. Every unsubscribe address is a new external recipient. Going over can block sending for up to 24 hours, and "the account might be suspended" ([Workspace limits](https://knowledge.workspace.google.com/admin/gmail/gmail-sending-limits-in-google-workspace?hl=en)). Many undeliverable messages also cause blocks on consumer Gmail. Workspace admins can restrict "high-risk" Gmail access such as sending mail to trusted apps only ([Workspace API controls](https://knowledge.workspace.google.com/admin/apps/control-which-third-party-and-internal-apps-access-google-workspace-data)). Cluster could keep reading and filing in such a tenant and still get a 403 on send.

On Outlook, both `sendMail` and sending a draft list **Mail.Send as the only permission** ([Graph sendMail](https://learn.microsoft.com/en-us/graph/api/user-sendmail?view=graph-rest-1.0), [Graph message send](https://learn.microsoft.com/en-us/graph/api/message-send?view=graph-rest-1.0)). `Mail.ReadWrite` can create a draft but not send it. Graph also has a beta `unsubscribe` action that "submits an email request on behalf of the signed-in user." It works only for mailto senders, needs Mail.Send, and **moves the message to Deleted Items** on success ([Graph unsubscribe](https://learn.microsoft.com/en-us/graph/api/message-unsubscribe)). Cluster should not use it. It hides the subject and body it sends, which defeats the confirm, and it deletes a message the user did not ask to delete. Mail.Send is normally consentable by the user. But Microsoft recommends tenants allow user consent only for verified publishers, and some tenants switch it off ([Entra user consent](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/configure-user-consent)). Exchange Online caps a mailbox at 10,000 recipients a day and 30 messages a minute ([Exchange limits](https://learn.microsoft.com/en-us/office365/servicedescriptions/exchange-online-service-description/exchange-online-limits)). Outlook.com allows Microsoft 365 subscribers **1,000 "non-relationship" recipients a day**. Free accounts get lower limits that Microsoft does not publish ([Outlook.com limits](https://support.microsoft.com/en-us/office/sending-limits-in-outlook-com-279ee200-594c-40f0-9ec8-bb6af7735c2e)). Graph returns 202 on send, which "doesn't indicate that the request processing has completed." Only a bounce in the inbox would show a failure.

Policy is where the draft plan breaks. The Chrome Web Store says extensions must not "**send messages on behalf of the user without giving the user the ability to confirm the content**," and that "the outcome of any user interaction should match the reasonable expectations that were set" ([CWS Program Policies](https://developer.chrome.com/docs/webstore/program-policies/policies)). A one-time "yes, do this automatically" does not let the user confirm the content of later messages. Google's User Data Policy also requires disclosure of "any actions you take on a user's behalf," made "prominent and timely" ([User Data Policy](https://developers.google.com/terms/api-services-user-data-policy)). No new scope means the consent screen does not change. The privacy policy, the store listing and the `gmail.modify` justification in the verification record should still say that Cluster sends unsubscribe emails when the user asks. The CASA security assessment is tied to restricted data stored on or sent through servers ([restricted scope verification](https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification)), so sending from the device does not change Cluster's position there. No Google statement says whether new use of an approved scope triggers re-review.

A prefilled compose window is the fallback that needs no scope and no policy reading. Gmail's undocumented `https://mail.google.com/mail/?view=cm&fs=1&to=…&su=…&body=…` URL can target an account and puts sending under the user's hand ([Simon Willison](https://til.simonwillison.net/google/gmail-compose-url)). The format could change without notice. Outlook's web compose deeplink was not verified from Microsoft docs.

## The gate must check the header, the address and the account

Unsubscribing from spam confirms a live address. RFC 8058 calls an unsubscribe "a strong hint to the mailer that the address to which the message was sent was valid" ([RFC 8058](https://www.rfc-editor.org/rfc/rfc8058.html)). Spamhaus says "never opt-out of lists that you did not opt-in to" ([Spamhaus](https://www.spamhaus.org/consumer/)). A mailto is a stronger signal than a POST, because it carries the user's real address in From. The only government test is old. In 2002 the FTC sent 215 remove requests and found "no evidence" of more spam, but about two thirds went to dead addresses, which would now be bounces against the user's account ([Techdirt](https://archive.techdirt.com/articles/20020405/0935251.shtml)). The real attack is documented. A "fake unsubscribe" campaign in 2019 to 2021 opened a prefilled mailto to 15 to 20 attacker addresses, and a test account was flooded with spam within days ([HKCSS, citing BleepingComputer](https://itsecurity.hkcss.org.hk/watch-out-these-unsubscribe-emails-only-lead-to-further-spam/)). Researchers also found 5 of 20 mail clients would attach local files from a mailto parameter ([study PDF](https://www.edumaps.de/media/2020-08-18-email-clients-vulnerable-to-attacks-via-mailto-links.pdf)). Cluster's API path cannot attach files, but the lesson is the same. The URL is a template written by the sender.

The draft's two rules hold up. "Never on Spam" matches every provider. Gmail shows unsubscribe only for senders "we're pretty sure are not spammers" ([Spam Resource](https://www.spamresource.com/2016/12/list-unsubscribe-on-gmail-frequently_19.html)), and Outlook drops junked mail from its subscription list ([Microsoft Support](https://support.microsoft.com/en-us/office/how-to-manage-email-subscriptions-in-outlook-com-26c8f447-2141-4bff-8781-80a4e6b7f0c8)). "Never on failed authentication" matches RFC 8058's DKIM rule. But the gate needs more than these two. The strongest single check is that a passing DKIM signature lists `list-unsubscribe` in its `h=` tag. Cluster already reads that tag for one-click in `hasVerifiedOneClickSignature`, so the mailto check reuses it, without the `list-unsubscribe-post` part. Google's own docs require List-Unsubscribe to be DKIM-signed ([Google 12811169](https://support.google.com/mail/answer/12811169)).

The address check needs care. No provider publishes a rule that the mailto host must match the From domain. A strict match would reject many real senders, because email services host the unsubscribe mailbox on their own domains, such as createsend.com for Campaign Monitor and hubspotemail.net for HubSpot ([Newsletrix](https://newsletrix.com/blog/how-to-tell-what-platform-a-newsletter-uses)). The workable rule is that the mailto's registrable domain equals one of these: the aligned From domain, the domain of a passing DKIM signature that covers List-Unsubscribe, the SPF-passing Return-Path domain, or a known email-service domain. Anything else goes to the user as a compose window.

| Gate check | Pass | Fail goes to |
|---|---|---|
| Location | Not in Spam or Junk, not flagged by Cluster's phishing checks | Block or report, no request |
| Authentication | DMARC pass, and a passing DKIM signature covers `list-unsubscribe` | Compose window, user decides |
| Recipient | Exactly one address after decoding, no cc, bcc or extra `to=` | Refuse |
| Address domain | Matches From, DKIM d=, Return-Path, or a known email-service domain | Compose window |
| Not the user | Not the user's own address, own domain, or a role address there | Refuse |
| Fields | Only subject and body kept. No CR or LF outside the body. Subject and body under a length cap | Refuse |
| Scheme | Only `mailto:` and `https:` accepted anywhere in the header | Drop the item |
| Account | The subscribed address is a send-as identity of this account | Ask the user, or compose window |
| Volume | Under the per-run and per-day caps, no recent send errors or bounce spike | Pause the run |

Privacy is the cost the user accepts. A sent mailto reveals the address, display name, send time with time-zone offset, and a Message-ID that shows the provider ([RFC 6068](https://www.rfc-editor.org/rfc/rfc6068.html)). Senders often put a per-recipient token in the mailto address, so they learn exactly who acted ([Mapp docs](https://documentation.mapp.com/1.0/en/list-unsubscribe-headers-12575935.html)). That is why the gate is about the sender's legitimacy and not about whether a token is present. It is also why a verified one-click POST should win whenever it exists. It reveals less and leaves nothing in Sent.

## The full process, from Unsubscribe to a verified result

The edge cases decide most of the design. Gmail's own unsubscribe covers "all of that sender's active mailing lists" and then sends new mail to Spam ([Gmail Help](https://support.google.com/mail/answer/15621070)). Clean Email groups by unsubscribe link instead ([Clean Email help](https://clean.email/help/unsubscriber/overview)). Unsubscribing from marketing leaves receipts and password resets flowing. CAN-SPAM treats those as transactional, and Google requires one-click "only for marketing and promotional messages" ([FTC](https://www.ftc.gov/business-guidance/resources/can-spam-act-compliance-guide-business), [Google FAQ](https://support.google.com/a/answer/14229414)). So a backstop filter on a whole domain will catch mail the user needs. No product can undo an unsubscribe on the sender's side. Clean Email's "Unblock" only stops its own filtering, and the user must contact the sender to get mail again ([Clean Email help](https://clean.email/help/unsubscriber/overview)). For results, Leave Me Alone is the only tool with documented failure evidence, an "Action required" flag with the reason ([Leave Me Alone help](https://help.leavemealone.com/en/troubleshooting/im-still-getting-emails)). For timing, Gmail and Yahoo expect bulk senders to stop within 2 days ([Yahoo Sender Hub](https://senders.yahooinc.com/best-practices/)). CAN-SPAM allows 10 business days ([FTC](https://www.ftc.gov/business-guidance/resources/can-spam-act-compliance-guide-business)). CASL is reported to use the same 10 days ([Bennett Jones](https://www.bennettjones.com/Insights/Blogs/2015/11/Unsubscribe-Problems-Nets-Telecommunications-Provider-Under-Antispam-Law)). The UK and India deadlines were not confirmed, so the copy should not name them.

The table is the recommended process. It replaces the draft plan.

| Step | What Cluster does | Notes |
|---|---|---|
| 1. User presses Unsubscribe | Collect every distinct List-Unsubscribe target for the chosen sender or senders, per account | One request per distinct target. De-duplicate by mailto address |
| 2. Pick the method | Verified one-click POST if present. Else mailto if it passes the gate. Else open the web link | One-click needs no Sent copy and reveals less |
| 3. Run the gate | Apply every check in the gate table | Failures become "Needs you" with a compose window or the link |
| 4. Pick the identity | Find the delivered-to address from To, Cc, Delivered-To, X-Original-To or a VERP Return-Path. Match it to `sendAs.list` | Plus-addresses and forwarded mail that is not a send-as identity get a warning or a question |
| 5. Build the message | One To, URL subject or "unsubscribe", URL body or empty, decoded once. No footer, no signature, no Auto-Submitted, not threaded | Cap subject and body length |
| 6. Confirm | A sheet lists each email: from, to, subject, body. Plain line: "Cluster will send these from your account. They will show in Sent." Button: "Send N emails". Cancel and per-row remove | Required every run. Single items get the same sheet with one row. No background or scheduled sends |
| 7. Queue | Write each item to `chrome.storage` with an idempotency key before sending | A closed browser resumes without double sends |
| 8. Send | Gmail: `messages.send`, a few seconds apart, about 20 per run and a daily cap well below 500. Outlook: Mail.Send if granted, else create a draft and open it for the user | On 403 or a sending-limit error, stop the run and offer compose windows |
| 9. Record | Save sender, target, method, identity, time, and the sent message ID. Check the response carries the `SENT` label | Shows in the Unsubscribed tab |
| 10. Backstop filter | Label "Unsubscribed" and skip the inbox, keyed on the exact From address, only for mail that carries List-Unsubscribe | Never on a bare domain. Receipts and resets without the header still arrive |
| 11. Tell the user | "Request sent by email. Most senders stop within 2 days. The law allows up to 10 business days." | Different copy for one-click and web link |
| 12. Watch replies, 0 to 72 hours | Match mail from the target's domain or a mailer-daemon. Classify as confirmed, needs a click, auto-reply, or bounce | Never click links in a "confirm" email for the user |
| 13. Handle bounces | Mark the item failed. Offer the web link if one exists. Several bounces in a run pause sending | Bounces count against the user's account |
| 14. Verify at day 3 | No new list mail: "Stopped." New list mail: "Still sending" and offer "Send their mail to Trash" | Avoid "they ignored you" before about 14 calendar days |
| 15. Watch to day 14 | Keep counting caught messages. Final verdict at day 14 | New mail after a purchase reads "came back", not "failed" |
| 16. Undo | Remove the filter. Copy: "Cluster stopped filtering. To get their emails again, re-subscribe on their site." | The sent request cannot be recalled |

Several accounts and shared mailboxes follow from the same rules. Each linked account sends its own request, because each address and token differs. The UI can still show one row per list. In a delegated or shared mailbox, sending goes out "on behalf of" and a filter there affects everyone, so Cluster should ask first. If the user deletes the backstop filter, Cluster should mark the item "filter removed" rather than quietly recreate it.

## What the current plan is missing

The draft plan was: send mailto after asking once, empty body, show in Sent, add a backstop filter, offer Trash after 3 days, about 20 per run, never on Spam or failed-auth senders, and Mail.Send for Outlook. Checked against the evidence, it needs these changes.

| Draft says | Evidence | Change |
|---|---|---|
| Ask once, then automatic | CWS forbids sending without letting the user confirm the content. RFC 6068 says SHOULD NOT send without disclosing. RFC 2369 requires review | Confirmation sheet with full content on every run. No silent or scheduled sends |
| Empty body | Some lists put the command in `?body=`. Keyword parsers read subject or body | Use URL subject and body when given. Default subject "unsubscribe". Empty body only when the URL has none |
| Send from the account | Mailman and similar match the subscribed address. RFC 2369 B.1 | Pick the delivered-to alias via `sendAs.list`. Ask when unclear |
| Gate is Spam plus failed auth | Spam and auth are right but not enough. The fake-unsubscribe scam used many recipients | Add DKIM coverage of List-Unsubscribe, one recipient, field sanitising, domain relation, own-domain block |
| About 20 per run | Workspace trial allows 500 unique external a day. Free Outlook.com limits are unpublished. Bounces block sending | Keep 20 per run. Add a daily cap, spacing, and stop rules on errors and bounces |
| Outlook needs Mail.Send | True, and some tenants block it. Graph's unsubscribe action deletes the message and hides content | Ship drafts plus open-in-Outlook first. Make Mail.Send an opt-in. Do not use the Graph unsubscribe action |
| Not covered | No reply handling | Watch 72 hours for confirmations, auto-replies and bounces |
| Backstop filter for the sender | Domain filters catch transactional mail | Key on exact From and require the List-Unsubscribe header |
| Trash after 3 days | Mailto is slow and the legal window is 10 business days | Keep the 3-day offer, but word it as "still sending", not "ignored" |
| Not covered | Google requires disclosure of actions on the user's behalf | Update privacy policy, store listing and the scope justification |
| Not covered | MV3 workers stop at any time | Durable queue with idempotency keys |
| Not covered | Workspace admins can block sending | Handle 403 with a compose-window fallback |
| Not covered | Parser in `unsubscribe.ts` splits on all commas and keeps the last mailto | Rewrite to RFC 2369 and RFC 6068 rules |

## Ranked build list

Ranking puts safety and policy first, because a send that goes wrong reaches someone else's inbox and the user's account. Sizes are estimates.

| Rank | What | Why | How |
|---|---|---|---|
| 1 | Strict parser and sanitiser | Every later step trusts its output. The current parser breaks on commas and keeps the wrong item | Split on commas outside `<>`. Stop at the first bad item. Keep the first mailto. Decode once, `+` stays `+`. Keep `to`, `subject`, `body`. Refuse cc, bcc, extra recipients, CR or LF outside the body, unknown fields. Unit tests from the RFC 2369 and 6068 examples |
| 2 | Mailto gate | Spam senders and crafted headers are the main risks | Reuse `hasVerifiedOneClickSignature` without the Post header. Add the domain relation with a known email-service list confirmed from real headers. Block the user's own domain and role addresses |
| 3 | Confirmation sheet and disclosures | CWS rule and both RFCs. Without it the store can reject Cluster | One sheet per run listing from, to, subject, body. "Send N emails". Update privacy policy, store listing and Google verification text in the same release |
| 4 | Identity picker | Wrong From means a silent failure on the lists most likely to be mailto-only | Read To, Cc, Delivered-To, X-Original-To and VERP Return-Path. Match against `sendAs.list`. Warn on plus-addresses and forwards. Ask when unsure |
| 5 | Gmail send path with pacing | The sending limits and bounce blocks put the user's whole account at risk | `messages.send` with raw base64url MIME. Space sends a few seconds apart. 20 per run, a low daily cap. Stop on 403, limit errors or a bounce spike. Fall back to the compose URL |
| 6 | Durable queue | MV3 service workers stop without warning, and a double send looks like abuse | Persist each item with an idempotency key before sending. Resume on startup and alarms. Record the returned message ID |
| 7 | Backstop filter on list identity | It is what users feel as success, and it must spare receipts | Exact From plus List-Unsubscribe present. Label and skip the inbox. Pack into existing filters. Unsubscribed tab lists each item |
| 8 | Reply watcher | Confirmations and bounces decide whether mailto worked | Watch the change feed for 72 hours. Four classes: confirmed, needs a click, auto-reply, bounce. File confirmations, surface clicks as "Needs you", mark bounces failed |
| 9 | Verification and honest copy | Users need a result, and the wording must not overclaim | Day 3 "still sending" with a Trash offer. Day 14 final verdict. Copy: "Most senders stop within 2 days. The law allows up to 10 business days." |
| 10 | Outlook path | Mail.Send adds consent friction and some tenants block it | First ship: create a draft with `Mail.ReadWrite` and open it in Outlook on the web. Later: Mail.Send as an opt-in incremental consent through the same sheet |
| 11 | Undo and Pause | No one can recall a sent request | Undo removes the filter with plain copy. Pause gives a filter-only option that sends nothing and is fully reversible |
| 12 | Local counters | No outside data on mailto success exists | Count method, bounces, confirmations, day-3 and day-14 verdicts, and how many senders were mailto-only. Store counts only, never message data |

Several facts need a live test before rank 5 ships. Confirm that an API send gets the `SENT` label and shows in Sent. Record the exact errors Gmail returns at a sending limit. Check the Outlook web compose deeplink. And sample real headers to confirm the email-service domains used by the gate.

## Conclusion

The owner's instinct was right that Cluster should send mailto requests itself. Apple and Gmail both do, and leaving the user to press send loses most of them. The change is in where the trust sits. The draft trusted the user's first yes. The evidence says to trust the user's view of each message, and to treat the header as untrusted until DKIM and the gate say otherwise. That costs one extra tap per run. In return it keeps Cluster inside the store rules, gives the user an honest record in Sent, and stops a crafted header from sending mail anywhere the user did not see.

Mailto is now mostly the channel of small and old list servers. Those are the senders that check the From address and send confirmation emails. So the work that matters most is not the send call, which is a few lines. It is picking the right identity and reading the replies.
