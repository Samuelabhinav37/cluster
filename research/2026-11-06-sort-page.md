# Sort inbox page: research (2026-11-06)

Asked for: Sort inbox gets its own page with an animation and a report of the scan. Research only. Build later.

## What exists today (sortInbox.ts)

- The top-bar **Sort inbox** button (`#top-sort`) presses the hidden `#sort-inbox-btn`. The confirm, preview and progress still render in `#sort-inbox-bar` on the Labels page.
- Flow: `startSortFlow` → `rebuildSortPreview` (a plan per label: messages, files out or stays) → `renderSortPreview` (tick list + "Apply to N messages") → `applySortPlan`.
- `applySortPlan` loops over labels and calls `provider.labelMessages` once per label. Then it logs `logAction("sort", "Sorted N into …")` with undo data (`via: "unsort"`), records the labels it created, saves `enabledBuckets` and syncs Gmail filters (`syncGmailCategoryFilters`).
- Progress is a single "Sorting…" line. It ends as "✓ {summary}" or "Sort failed, try again".
- What the page can show without new data: the plan (labels, counts, files out or stays), per-label done/failed as the loop runs, the labels created, the filters synced, and an undo per label from the action log.

## Patterns worth copying

Read from how these products behave, not re-measured this round:

- **Mercury transfers.** Review, then submit, then a status page. The status page is the receipt and has a single primary action. Cluster can do the same: Plan → Sorting → Report, all on one route.
- **Plausible.** One number on top, then rows with a share bar behind them. The report reuses Cleanup's `.pl-card` / `--share` rows: one row per label with its count and share of the sort.
- **Apple Photos import / Time Machine.** Progress shows the item being worked on plus a determinate bar. Use a determinate bar only when the total is known. Here it is known: the total comes from the plan.
- **Gmail's own toast** ("Conversation moved to X · Undo"). Undo sits next to the result and is not buried in a log.

## Proposed page (for the build)

The route is `data-screen="sort"`. The sidebar keeps the normal nav, and the top-bar button opens this screen.

1. **Plan.** Title "Sort inbox". There is no KPI strip, only one bare number ("2,607 emails"). Each label is a row: Gmail tag icon (`gmailLabelIcon`), name, count with a share bar, and "Files out" / "Stays" as gray text. A row expands to show its messages and their ticks (the existing preview list). One button: **Sort**.
2. **Sorting (the animation).**
   - Each label row's share bar fills from left to right while that label's `labelMessages` call runs. A bar is one label's batch, so this is real progress and not a fake timer.
   - A single line under the title counts up: "1,240 of 2,607".
   - Finished rows get a check, and the tag icon nudges once (a short translate). Nothing loops.
   - With `prefers-reduced-motion`, there are no fills or nudges, only the count.
   - Needed for the build: `applySortPlan` takes an `onProgress(entryIndex, doneCount)` callback. It is a small change, because the loop is already per label.
3. **Report (the scan report).** It replaces the progress in place:
   - "2,607 emails sorted", plus the time it took.
   - Rows per label: the count, files out or stays, and an **Undo** link built from the matching `logAction` entry. The undo path already exists.
   - "Kept sorting: N labels". These are the Gmail filters synced, and the line links to Labels.
   - Created labels are listed once, in gray.
   - Failures: the row turns red with **Try again** for that label only. Today one failure fails the whole sort.
   - The report is kept as the last sort report. Overview's scan card can link to it.
